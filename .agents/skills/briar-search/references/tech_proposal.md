# 500 个本地代码仓库跨业务域语义检索技术方案

> **调研目标**：评估通过 DeepWiki、Obsidian 等工具实现"跨仓库业务语义搜索"的可行性，并给出可落地的本地部署架构与实施路线图。
> 
> **核心诉求**：
> 1. 自然语言搜索业务概念（如"导购换绑"），召回相关仓库及文件；
> 2. 模糊定性业务归属（导购 / CRM / 支付等），返回相关仓库集合；
> 3. 全部基于本地 500 个私有仓库运行，无代码外泄风险。

---

## 一、可行性结论：DeepWiki / Obsidian 均不适用

### 1.1 DeepWiki（含开源版 DeepWiki-Open）

| 维度 | 官方版 | DeepWiki-Open（本地部署版） |
|------|--------|---------------------------|
| **核心能力** | 为单个 GitHub 仓库生成结构化的 AI Wiki 文档 | 为单个本地仓库生成 AI 文档 |
| **跨库检索** | ❌ 不支持 | ❌ 不支持 |
| **私有仓库** | 需付费 Devin 账号 | ✅ 支持 |
| **图谱能力** | 仅生成单仓库目录树，无业务关系 | 仅单仓库目录树 |
| **语义搜索** | ❌ 无 | ❌ 无 |

**结论**：DeepWiki 本质是**单仓库文档生成器**，其技术路线是"理解一个仓库"，而非"在多个仓库间联合检索"。对于"搜导购换绑，跨 50 个导购域仓库找到相关代码"的诉求，DeepWiki 无法提供任何跨库索引或检索机制。

### 1.2 Obsidian

| 维度 | 现状 |
|------|------|
| **核心定位** | Markdown 双向链接笔记工具 |
| **图谱本质** | 笔记之间的 `[[链接]]` 关系图谱 |
| **代码适配** | 无原生代码索引能力，需通过插件手动导入 |
| **语义搜索** | 依赖 Smart Connections 等插件的 BM25 + 简单向量匹配 |
| **批量处理** | 500 个仓库的 AST 解析、向量化、关系抽取无现成工作流 |

**结论**：Obsidian 是知识管理工具，不是代码搜索引擎。把 500 个代码仓库 ETL 成 Obsidian 笔记来跑"图关系"，属于**用错工具**——它的图谱反映的是"哪篇笔记引用了哪篇"，而不是"导购业务依赖了哪些仓库的哪些接口"。实施成本极高且效果不可预期。

### 1.3 方向修正：放弃"文档工具路线"，走"搜索引擎 + 语义层"路线

真正的技术方向是构建一个**本地部署的代码混合搜索引擎**，在代码全文索引之上叠加**业务域标签**与**语义向量**，实现自然语言到代码的跨域映射。

## 二、推荐架构：三层混合检索引擎

### 2.1 架构总览

```
┌─────────────────────────────────────────────────────────────────────┐
│                         查询层 (Query Layer)                        │
│              自然语言输入："导购换绑" / "CRM客户归属查询"              │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                    混合检索引擎 (Hybrid Search)                     │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────────────┐   │
│  │  BM25 全文检索  │  │  业务域标签过滤 │  │  向量语义相似度排序    │   │
│  │  (Zoekt)       │  │  (业务元数据)   │  │  (Qdrant + CodeEmbed) │   │
│  └────────────────┘  └────────────────┘  └────────────────────────┘   │
│                              ↓ 加权融合排序                            │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                        索引层 (Index Layer)                         │
│  ┌─────────────────┐ ┌─────────────────┐ ┌──────────────────────────┐  │
│  │  Zoekt / Tantivy │ │  Qdrant 向量数据库 │ │   业务域元数据 (标签库)   │  │
│  │  代码全文索引     │ │  代码语义向量      │ │   仓库-域-功能映射关系    │  │
│  └─────────────────┘ └─────────────────┘ └──────────────────────────┘  │
└─────────────────────────────┬───────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│                        数据层 (Data Layer)                          │
│    500 个本地 Git 仓库 → AST 解析 → 语义分块 → 向量化 → 业务域打标     │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 架构设计原则

| 原则 | 说明 |
|------|------|
| **分层解耦** | 全文索引、向量索引、业务标签三者独立存储，可单独升级或替换 |
| **混合检索** | 关键词精确匹配（BM25）负责召回，语义向量负责精排，业务标签负责筛选 |
| **本地优先** | 所有组件均支持本地 Docker 部署，代码与索引不出内网 |
| **渐进建设** | 分三期实施，第一期即可产出可用效果，无需等待完整图谱 |

## 三、核心组件选型与技术论证

### 3.1 全文索引层：Zoekt（强烈推荐）

#### 选型理由

- **Google 出品**，Sourcegraph、GitLab 等企业级代码搜索的底层引擎；
- 基于**三元组索引（Trigram Index）**，支持子串搜索、正则表达式、布尔查询；
- 索引性能经过大规模验证，500 个仓库（约 50GB 源码）无压力；
- 索引体积约为源码的 **3.5 倍**，100GB 代码约 350GB 索引文件；
- 提供 **JSON API + Web UI**，便于二次封装。

#### 关键特性对比

| 特性 | Zoekt | Hound | Sourcebot | Livegrep |
|------|-------|-------|-----------|----------|
| 正则搜索 | ✅ 原生支持 | ⚠️ 有限 | ✅ 支持 | ✅ 支持 |
| 本地仓库 | ✅ 直接支持 | ✅ 支持 | ✅ 支持 | ⚠️ 需配置 |
| Web UI | ✅ 内置 | ✅ 内置 | ✅ 更现代 | ✅ 内置 |
| 索引增量更新 | ✅ 支持 | ❌ 全量重建 | ✅ 支持 | ⚠️ 有限 |
| 索引体积 | ~3.5x 源码 | ~2x 源码 | ~3.5x 源码 | ~2.5x 源码 |
| 部署复杂度 | 低 | 低 | 中 | 中 |

#### 基础部署示例

```bash
# 1. 安装/编译 zoekt
# 二进制可从源码编译或使用 Docker

# 2. 对 500 个仓库批量建立索引
zoekt-git-index -index ~/.zoekt \
  /path/to/repo1 \
  /path/to/repo2 \
  ...

# 3. 启动 Web 服务与 RPC 接口
zoekt-webserver --index ~/.zoekt -rpc -listen :6070
```

#### 与业务域结合

在 Zoekt 查询中直接加入仓库过滤条件，实现"先按业务域筛选，再在域内全文检索"：

```
content:rebind AND (repo:guide-* OR repo:shop-* OR repo:导购*)
```

### 3.2 向量语义层：Qdrant + FastEmbed

#### 选型理由

| 组件 | 选型 | 核心优势 |
|------|------|---------|
| 嵌入库 | **FastEmbed** | Qdrant 官方出品，轻量纯 CPU，无需 GPU，内置代码友好模型 |
| 向量库 | **Qdrant** | 开源、Docker 一键部署、原生支持混合检索（BM25 + 向量）、过滤查询 |
| 分块器 | **Tree-sitter** | 基于 AST 的结构化分块，保持函数/类/方法完整性，避免按行截断 |

#### 代码分块策略（关键设计）

**错误做法**：按固定行数（如每 100 行）切分代码块，导致函数被截断、语义破碎。

**正确做法**：基于 Tree-sitter AST 提取**语义完整单元**：

| 提取单元 | 提取内容 | 业务语义价值 |
|---------|---------|-------------|
| 函数定义 | 函数签名 + Docstring + 核心逻辑 | 最高，直接对应业务功能 |
| 类/结构体定义 | 类名 + 字段 + 方法列表 | 高，对应业务实体 |
| 接口/协议定义 | API 路径、Proto 定义 | 高，对应系统交互边界 |
| 配置文件块 | Service 注册、路由映射 | 中，对应服务编排关系 |

#### 业务域标签增强向量化

在文本向量化前，将业务域标签**前置注入**，强制提升语义关联：

```python
# 原始代码块
def rebind_user_guide(old_guide_id, new_guide_id, user_id):
    """导购换绑：将用户从原导购迁移至新导购"""
    pass

# 增强后的向量化文本
"[业务域:导购] [功能:换绑] [类型:服务函数] def rebind_user_guide(...)"
```

这样即使查询词是"导购换绑"而非代码符号 `rebind_user_guide`，向量相似度也能显著高于无标签文本。

### 3.3 业务域打标层：LLM + 规则混合策略

这是解决"模糊定性业务归属"的核心。采用**规则先验 + LLM 精标**的两级策略。

#### 第一级：启发式规则（高置信度自动打标）

| 规则类型 | 示例 | 标签动作 |
|---------|------|---------|
| 目录/包名 | `com.company.guide.*`、`/guide/` | 标记 `导购` |
| 目录/包名 | `*crm*`、`/customer/`、`/client/` | 标记 `CRM` |
| 目录/包名 | `*payment*`、`/pay/`、`/billing/` | 标记 `支付` |
| 接口路径 | `/api/v1/guide/rebind` | 标记 `导购` + `换绑` |
| README 关键词 | 标题或首段含"导购" | 标记 `导购` |

#### 第二级：LLM 语义精标（低置信度人工复核）

对于规则未覆盖或冲突的仓库，使用**本地 LLM**（通过 Ollama 部署 Qwen / CodeQwen）分析 README 与目录结构：

```json
{
  "repository": "user-attribution-service",
  "business_domain": "导购",
  "functions": ["归因", "绑定关系查询", "业绩分配"],
  "confidence": 0.87,
  "reasoning": "README 提到导购员业绩归属，接口路径含 guide/attribution"
}
```

**本地 LLM 资源要求**：7B 参数模型（如 Qwen2.5-Coder-7B）可在 CPU 上运行，16GB 内存即可满足单并发打标。

---

### 3.4 知识图谱层（可选增强）：Neo4j 业务图谱

如果第三期需要支持"导购有哪些核心功能？""导购和 CRM 的交互点在哪些仓库？"这类图谱遍历查询，可引入轻量级 Neo4j。

#### 图谱 schema 设计

```cypher
(:BusinessDomain {name: "导购"}) -[:HAS_FUNCTION]->
(:BusinessFunction {name: "换绑"})

(:BusinessFunction) -[:IMPLEMENTED_IN]->
(:Repository {name: "guide-rebind-service", path: "/repos/guide-rebind-service"})

(:Repository) -[:CONTAINS]->
(:CodeUnit {type: "function", name: "rebind_user_guide", path: "src/service/rebind.go"})

(:CodeUnit) -[:CALLS]-> (:CodeUnit)
```

#### 抽取与构建方式

1. **LLM 抽取**：从 README、接口文档、代码注释中提取 `业务域-功能-仓库` 关系；
2. **静态分析补充**：通过导入关系、调用链（call graph）补充代码结构边；
3. **增量更新**：每次代码提交后，仅更新受影响子图。

## 四、完整技术栈选型表

| 架构层级 | 职责 | 推荐选型 | 备选方案 |
|---------|------|---------|---------|
| 代码全文索引 | 快速关键词/正则召回 | **Zoekt** | Hound, Sourcebot, Livegrep, Tantivy |
| 向量存储 | 语义向量存储与相似度计算 | **Qdrant** | Chroma, Weaviate, Milvus |

| 图谱存储 | 业务关系可视化与遍历 | **Neo4j**（可选） | PostgreSQL JSONB（轻量版）|
| 搜索前端 | 用户查询与结果展示 | **自建 Web（React/Vue）** | Zoekt 原生 Web UI |
| 任务调度 | 索引更新、打标流水线 | **Temporal / Airflow** | 简易 Cron + Python 脚本 |

## 五、实施路线图

### 5.1 第一期：基础全文搜索 + 业务域筛选（1–2 周）

**目标**：让"搜关键词 + 按业务域筛选"立刻可用。

| 任务 | 输出 |
|------|------|
| 搭建 Zoekt 索引服务，批量导入 500 个仓库 | 统一代码搜索入口 |
| 编写业务域规则脚本，基于仓库名/目录名/包名自动打标 | 每个仓库打上 1-N 个业务域标签 |
| 封装搜索 API：支持 `query + domain_filter` | 前端或命令行可按"导购"筛选搜"rebind" |
| 部署 Zoekt Web UI 或简易前端 | 团队可开始使用 |

**预期效果**：
- 搜索 `rebind` + 筛选 `导购` → 返回导购域仓库中包含 rebind 的文件列表；
- 搜索响应时间 < 1 秒；
- 无需向量或 AI，即可解决 60% 的"我知道大概代码符号"类查询。

---

### 5.2 第二期：语义向量搜索上线（2–3 周）

**目标**：支持自然语言搜索，无需知道代码符号。

| 任务 | 输出 |
|------|------|
| 基于 Tree-sitter 编写多语言（Java/Go/Python/JS）AST 提取脚本 | 全量代码语义分块 |
| FastEmbed 向量化所有代码块，注入业务域标签前缀 | Qdrant 向量库就绪 |
| 实现混合检索：Zoekt BM25 粗排 + Qdrant 向量精排 | 自然语言查询可用 |
| 查询改写：简单 query 扩展（"导购换绑" → "导购 换绑 guide rebind"）| 提升召回率 |

**预期效果**：
- 搜"导购换绑" → 召回 `rebind_user_guide`、`GuideRebindService` 等语义相关代码；
- 搜"CRM 客户归属查询" → 召回 CRM 域的客户查询相关接口与实现；
- 解决"我不知道代码里怎么写的，只知道业务说法"类查询。

---

### 5.3 第三期：知识图谱与智能归因（3–4 周）

**目标**：支持模糊业务归因、跨域关系查询、需求影响分析。

| 任务 | 输出 |
|------|------|
| 用 LLM 抽取仓库 README、接口文档中的 `业务域-功能-仓库` 关系 | 结构化业务元数据 |
| Neo4j 建图，融合 LLM 抽取关系 + 静态分析调用关系 | 可查询的业务知识图谱 |
| 实现图谱查询接口："导购依赖哪些下游系统？" | 关系型问答可用 |
| 增量索引流水线：Git hook / CI 触发局部更新 | 代码更新后索引自动同步 |

**预期效果**：
- 输入一个需求描述，系统可返回"涉及业务域：导购、CRM；涉及仓库：guide-service、crm-attribution、user-sync"；
- 输入一个仓库，系统可回答"这个仓库属于导购域，核心功能是用户换绑与业绩归因"。

## 六、资源与性能估算（本地部署）

以 **500 个仓库、总源码约 50GB** 为基准估算：

| 资源项 | 估算值 | 说明 |
|--------|-------|------|
| Zoekt 全文索引 | ~150GB 磁盘 | 3.5 × 源码体积 |
| Qdrant 向量索引 | ~20GB 磁盘 | 假设 100 万个代码块，768 维 float32 向量 + payload |
| 运行内存 | 32GB+ | Zoekt 查询缓存 + Qdrant 驻内存索引 |
| CPU | 16 核+ | AST 解析、向量化、LLM 推理并发 |
| GPU | 非必需 | FastEmbed 与 7B 本地模型 CPU 可流畅运行 |
| 首次全量索引时间 | 4–8 小时 | 取决于仓库总大小与 CPU 性能 |
| 增量索引时间 | 分钟级 | 单次提交触发局部更新 |

## 七、风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 500 个仓库代码风格差异大，AST 解析覆盖不全 | 部分语言分块质量差 | 优先支持主力语言（Java/Go），其他语言退化为正则分块 |
| 业务域边界模糊（如导购和 CRM 共用仓库） | 标签置信度低 | 支持多标签（`["导购", "CRM"]`），搜索时按包含关系召回 |
| 首次全量向量化耗时过长 | 二期上线延迟 | 分批次并行处理，或夜间离线流水线执行 |
| 自然语言查询与代码语义 gap 大 | 向量召回不准 | 持续优化 prompt 注入标签，必要时引入 Query2Doc 扩展 |

## 八、结论与行动建议

### 8.1 核心结论

| 原想法 | 可行性 | 结论 |
|--------|--------|------|
| DeepWiki 跑图关系 | ❌ 不可行 | 单仓库文档工具，无跨库检索能力 |
| Obsidian 跑图关系 | ❌ 不可行 | 笔记工具，非代码搜索引擎，ETL 成本极高 |
| 直接构建完整 Graph RAG | ⚠️ 可行但过重 | 可作为远期目标，不建议作为起点 |
| **Zoekt + Qdrant + 业务标签** | ✅ **推荐** | 分层渐进，第一期即可产出可用效果 |

### 8.2 立即行动项

1. **验证 Zoekt**：挑选 10–20 个代表性仓库，本地部署 Zoekt 验证索引速度与搜索体验；
2. **梳理业务域规则**：整理你现有的导购 / CRM / 支付等业务域关键词，写成第一批正则打标规则；
3. **确认仓库规范**：检查 500 个仓库的目录结构、包命名是否有规律可循，这直接决定规则打标的准确率；
4. **定义一期界面**：确定搜索入口形式（Web 页面 / IDE 插件 / 命令行），预留 API 接口规范。
